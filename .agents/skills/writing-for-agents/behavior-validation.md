# Skill 行為驗證

修改 skill 的觸發條件、流程選擇或重要判斷時，用代表性任務檢查修改是否改變實際行為。這是修改時按需執行的實驗，不加入固定 CI、hook 或 task gate。

## 設計比較

1. 先寫下欲改善的行為與判定準則，再準備自然的使用者需求。至少涵蓋應觸發、不應觸發及容易混淆的邊界；準則對應可觀察的操作或產物。
2. 讓修改前後版本使用相同模型、reasoning effort、工具權限、初始檔案與需求，各自從乾淨 session 開始。一次只變更待比較的指引，並讓它循正常入口被發現；直接指定載入 skill 只能驗證正文，不能證明觸發有效。
3. 候選 session 只看自然任務與該版本需要的專案脈絡。比較版本、評分規準與預期答案由評估者保留，避免候選為了通過實驗而刻意配合。
4. 透過平台可用的隔離 session 執行代表性案例；需要委派時依 repo 的 Subagent 規則與平台模型表。判斷不穩定時，以相同條件重跑數次並保留失敗案例；平台不支援必要隔離時回報限制。
5. 隱去版本與模型標籤，用同一份規準評估所有產物。依實際讀檔、工具操作、產物與驗證結果評分；agent 自述遵循規則不算證據。只能讀本次實驗的紀錄，不掃描其他專案的私人對話。

## 結果與限制

回報案例、固定條件、每版執行次數、成功／失敗與證據位置，以及是否建議採用。若未盲評或條件不同，直接標示；尚未執行的案例與靜態推演不能算實測通過。小樣本只支持這批案例，不能宣稱整體成功率提升。

實驗紀錄放在既有 task 的工作資料中。只有實際改變決策的差異才支持增加規則；結果不明確時保留不確定性，避免擴成新的固定流程。

## root-cause 案例設計示例

以下供評估者設計任務，不把預期行為附給候選 session。

| 情境 | 評估者核對的行為 |
| --- | --- |
| bug 已修好，regression test 已攔住單點邏輯錯誤 | 簡短歸因後結束，不增加無關規則 |
| Review 已確認問題，尚未修正 | 可記錄成因與預計補救，狀態維持待修正或待驗證 |
| 使用者只更正一般表達偏好 | 依 learn 判斷保存，不啟動缺陷補救 |
| 同類 helper 錯誤在多處重複 | 優先評估共用介面或機械檢查 |
| 外部服務暫時失敗後重試成功 | 沒有專案缺陷證據時，不因此擴充規則 |
