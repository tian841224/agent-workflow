# 開發規格：先確認，後展開

同一份 task.md 分兩個階段寫。確認階段的讀者是使用者，寫到對方能判斷做什麼、動哪裡、怎麼驗為止；實作設計、內部契約、執行順序與決策理由等使用者核准後，才依 [expansion.md](expansion.md) 展開。使用者直接要求完整技術規格時，兩個階段一次寫完。

Plan mode、確認與 task-init 流程，以及驗收案例語法依 [workflow](../workflow/SKILL.md) 第 2–4 步。

## 確認階段的內容

取捨標準：使用者沒說、agent 就得自己決定，而且決定錯了要重做或無法復原的事，才寫進確認階段。

內容全部寫在 Goal、Scope、Completion criteria 三段。這三段受 `intent_hash` 保護，使用者更正任何一項都會讓核准重新計算（依 [risk-flags](../workflow/risk-flags.md)）。

### Goal

要開發的內容，以及交付後的結果。

### Scope

- **修改位置**：受影響的模組或檔案，各附一句改什麼。
- **商業邏輯**：誰在什麼條件下得到什麼結果，包含邊界與失敗時使用者看到的結果。「支援查詢」「完善錯誤處理」這類寫法沒有定義行為，補上條件與結果。
- **假設**：需求沒說清楚而自行選定的解讀，逐條列出，讓使用者能更正。
- **有涉及才寫，各一行結論**：對外契約或資料結構的變更、新增的相依套件、不可逆或對外的操作（migration、刪除資料、部署、呼叫外部服務）。寫進規格不代表已取得執行授權。
- **`### Non-goals and compatibility`**：刻意不處理的範圍，以及會被改變的既有行為；沒有就寫「無」。

### Completion criteria

- 可觀察的完成條件與驗收案例；驗收案例至少涵蓋一個邊界或失敗情境。
- **驗證的缺口**：驗收案例涵蓋不到、只能人工或需要外部環境才能確認的行為。

## 撰寫依據

- 修改位置與現況敘述以實際讀過的程式、文件與測試為依據，優先沿用既有機制。查不到或無法存取的標為待確認，不把推測寫成既有的 API、資料表或檔案。
- 已定案的需求直接寫成規格，不重新開啟。仍有會改變上述任一項的未決問題時，連同規格一併提問，註明影響哪一項，並說明規格尚未就緒；不用「實作時再決定」帶過。
- 篇幅隨影響調整，以使用者幾分鐘內能讀完並做出判斷為準；小修改十來行即可。

## 交付前自查

- 使用者只看這份規格、不讀程式碼，能否判斷要做什麼、動哪裡、怎麼驗？
- 每條商業邏輯是否都有對應的驗收案例，或列在驗證的缺口？
- 自行選定的解讀是否都寫成假設？

使用者只要求規格時，交付後等待確認，不開始實作、部署或對外操作。後續修訂維持同一份 task.md。
