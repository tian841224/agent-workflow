# 可交付的開發規格計畫

開發計畫的主體是「交付後的系統應如何運作，以及如何實作與驗收」，不是工作項目清單。完成後，另一位開發者應能依規格實作，驗收者應能依條件判定通過，不需自行補定產品規則或重要技術契約。

## 先取得實作依據

- 有程式碼或既有文件可讀時，查明相關入口、呼叫鏈、資料來源、現有介面與測試慣例，優先沿用既有機制。路徑與現況敘述須有實際依據；無法存取時明確標記待確認。
- 區分已確認需求、現況事實、設計決策、合理假設與待確認事項。不要把建議寫成既有功能，也不要虛構 API、資料表或檔案已存在。
- 已定案的需求直接深化為規格。只有會實質改變產品行為、資料安全或技術契約的未決問題才需要釐清；能獨立完成的部分持續補齊。
- 規格深度由受影響的行為與契約決定。小型修改可以短，但仍須說清楚交付結果與驗收條件；不為湊章節設計新機制。

## 規格內容

依專案文件慣例組織，至少涵蓋下列適用內容。可合併章節；不適用的項目略過，容易誤解的排除範圍則交代原因。

### 1. 目標、範圍與交付物

描述問題、觸發情境與預期結果，明確列出納入及排除的範圍。列出具體交付物，例如功能入口、受影響模組、API、migration、設定或文件；逐項說明內容、完成後的行為與完成條件。檔案清單只是定位，不能取代功能規格。

### 2. 功能與操作流程

以使用者或系統的觸發事件描述前置條件、輸入、處理規則、輸出與副作用。寫清楚正常流程、邊界條件、錯誤流程與相容性要求。涉及 UI 時，定義必要的欄位、操作、驗證、載入／空資料／失敗狀態與權限顯示。

避免「支援查詢」「完善錯誤處理」「確保一致性」等未定義行為；補上誰在什麼條件下，得到什麼結果。

### 3. 實作設計與責任邊界

說明變更應放在哪個既有模組、沿用哪些機制、各元件負責什麼，以及跨元件的呼叫或資料流。列出必要的修改點、相依關係與核心演算法；非顯而易見的決策補上理由。

實作細節須足以排除重要歧義，不必預寫所有程式碼。先採滿足需求的最小設計；僅在存在實際取捨時比較替代方案。

### 4. 介面與資料契約

涉及介面時，定義入口或方法、參數型別、必填性、預設值、有效範圍、回傳結構、錯誤語意與必要範例。涉及資料時，定義欄位、識別鍵、約束、來源與儲存方式。

時間、金額、排序、分頁、空值、權限與相容性等可能造成不同實作結果的語意，依需求明確定義。新增或變更的契約，應能對應到呼叫端與受影響資料。

### 5. 狀態、失敗與恢復

只補齊本次設計實際涉及的契約：狀態與轉移條件、重複請求、並行操作、交易邊界、逾時、部分失敗、重試與恢復。說清楚失敗時哪些資料已寫入、哪些副作用可能已發生，以及下一次操作的結果。

涉及資料或版本轉換時，定義 migration、既有資料處理、版本相容與必要的回復策略。規格中的部署或外部操作步驟不代表已執行或取得執行授權。

### 6. 驗收與驗證

每項主要需求及交付物對應可觀察的驗收條件。適合時使用表格：需求／情境、輸入與前置條件、預期輸出或狀態、驗證方式。

覆蓋正常流程與本次變更的關鍵邊界、失敗或恢復案例。指定適當的自動化測試、檢查命令或人工操作；命令需符合已確認的專案工具。沒有執行過的檢查標為「預定驗證」，不可宣稱已通過。區分本機驗證與需外部服務才能確認的結果。

### 7. 執行順序與未決事項

規格完成後才列必要的實作順序、相依關係與完成條件；工作步驟應引用前面的交付規格，不能取代規格。使用者要求一次完整設計時，在同一份計畫涵蓋完整交付範圍，不把必要契約延後到後續階段。

待確認事項須寫明影響哪個契約或驗收結果。若仍缺少阻擋實作的重要決策，明確說明規格尚未就緒，不用「實作時再決定」隱藏缺口。

## 交付前自查

- 開發者能否從規格決定輸入、輸出、修改位置、資料變化與失敗結果？
- 驗收者能否在不詢問作者的情況下，判斷每項主要交付物通過或失敗？
- 所有需求是否都有對應交付物與驗收條件，所有設計是否都在需求範圍內？
- 重要未知是否已標示，已確認的選擇是否被無故重新開啟？

若答案是否定的，先補上缺少的行為或契約，不以增加待辦項目代替。

## 輸出邊界

使用者只要求計畫時，交付規格，不自行開始實作、部署或對外操作。未要求檔案時可直接在對話提供；要求保存時，優先使用指定路徑或既有文件慣例。後續修訂維持同一份規格，避免產生互相矛盾的版本。
