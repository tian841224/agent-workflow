# 核准後展開

使用者核准確認階段的規格、task-init 完成後讀本檔。展開的目標：另一位開發者能依規格實作，驗收者能依條件判定通過，不需自行補定產品規則或重要技術契約。

## 何時展開、寫在哪裡

- 單一檔案、局部行為的修改直接實作，不展開。跨模組，或涉及契約、資料、狀態與失敗恢復的修改才展開；深度由受影響的行為與契約決定，不適用的章節略過，不為湊章節設計新機制。
- 先讀 task-init 回傳的 `context`（專案文件、記憶、改過同一批路徑的已結案 task），再寫設計。
- 寫在 task.md 的 Goal、Scope、Completion criteria 以外的章節。這些章節不在 `intent_hash` 內，增補不需要使用者重新確認。
- 展開時發現要改動行為、範圍、對外契約或驗收，就修改前三段並依 [workflow](../workflow/SKILL.md) 第 3 步重新取得確認；這類變更不能只寫在設計章節，程式修改以可執行的驗收案例涵蓋。
- 跨多個 task 的大型功能可沿用專案共用規格：task.md 引用該規格，保留本次範圍、必要契約與驗收案例。修訂時更新既有 owner 文件，不維護兩份重複的完整規格。

## 展開內容

### 實作設計與責任邊界

說明變更放在哪個既有模組、沿用哪些機制、各元件負責什麼，以及跨元件的呼叫或資料流。列出必要的修改點、相依關係與核心演算法；非顯而易見的決策補上理由。

細節寫到足以排除重要歧義，不預寫所有程式碼。先採滿足需求的最小設計；存在實際取捨時才比較替代方案。

### 介面與資料契約

涉及介面時，定義入口或方法、參數型別、必填性、預設值、有效範圍、回傳結構、錯誤語意與必要範例。涉及資料時，定義欄位、識別鍵、約束、來源與儲存方式。

時間、金額、排序、分頁、空值、權限與相容性等會造成不同實作結果的語意，依需求明確定義。新增或變更的契約要能對應到呼叫端與受影響資料。

### 狀態、失敗與恢復

只補齊本次設計實際涉及的部分：狀態與轉移條件、重複請求、並行操作、交易邊界、逾時、部分失敗、重試與恢復。寫清楚失敗時哪些資料已寫入、哪些副作用可能已發生，以及下一次操作的結果。

涉及資料或版本轉換時，定義 migration、既有資料處理、版本相容與必要的回復策略。

### 執行順序

列出必要的實作順序與相依關係，步驟引用前面的規格，不取代規格。expanded 任務的切片依 [elevated.md](../workflow/elevated.md#ordered-implementation-slices)。

## 展開後自查

- 開發者能否從規格決定輸入、輸出、修改位置、資料變化與失敗結果？
- 所有設計是否都在已確認的範圍內，所有已確認的需求是否都有對應的設計與驗收條件？
- 是否有重要行為或契約只寫在設計章節，沒有反映到前三段？

答案是否定時，補上缺少的行為或契約，不以增加待辦項目代替。
