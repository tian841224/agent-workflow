# PR／MR 規範

本文件規範 PR／MR 的標題、內文與建立方式。類型表與「內容只描述這次修改」依 [SKILL.md](SKILL.md)；push 的授權依入口文件的硬護欄。

## 內容來源

以遠端目標分支（例如 `origin/main`）與 HEAD 的差異為準，避免本機分支過期而把已合併的 commit 算進來。未指定目標分支時用 remote 的預設分支。

- 內容以 `git diff origin/<base>...HEAD` 的最終結果為準；`git log origin/<base>..HEAD` 的 commit 訊息只作為線索，分支中途加入後又改掉或移除的內容不寫。
- 工作樹中未 commit 的修改不會進入 PR／MR，不寫進內文；有這類修改時先告知使用者。

## 標題

```text
<類型>(<模組>): <大綱>
```

- 類型：依整個分支的主要變化，從 SKILL.md 的類型表選一個。
- 模組：整個分支只動到單一模組時才加；跨模組時寫成 `<類型>: <大綱>`。
- 大綱：一句話列出最主要的 2～3 項變化，結尾不加句號。

## 內文

內文分兩層：摘要用幾句話讓讀者知道這個分支改了什麼流程；每項改動的內容寫在設計說明。同一句內容在兩段都出現，代表摘要寫得太細。改了哪些檔案、函式、測試與文件由 diff 呈現，不另外列出。

| 段落 | 何時寫 | 寫什麼 |
| --- | --- | --- |
| 摘要 | 一律 | 改了什麼流程與目的 |
| 問題背景 | 修正 bug | 問題在什麼情境下發生 |
| 設計說明 | 有兩項以上的改動，或有技術上的調整要說明 | 每項改動的流程與技術上的調整內容 |
| 已知限制與可能異常 | 修改後仍有會出問題的情境，或有尚未實測的範圍 | 情境與發生時看到的現象 |

依表格順序排列，不符合「何時寫」的段落整段省略，不留空標題。

### 摘要

兩到四句，說明這個分支改了什麼流程與目的；修正 bug 時說明使用者在什麼情境下遇到什麼症狀。

- 一句說一件事，每句自成一段，中間空一行；不把幾件事擠在同一段。
- 只寫主流程：拿掉之後這個分支的目的就不成立的改動。其餘改動只寫在設計說明。
- 用流程與行為的說法，不帶函式、設定鍵、錯誤碼或狀態值。
- 不列出設計說明的標題；標題在設計說明看得到。

### 問題背景

只有修正 bug 時才寫；新增功能、調整流程與重構沒有這一段。依觸發順序列出問題怎麼發生，每步一句，用不熟悉程式的人也看得懂的說法。請求數、等待秒數等讓讀者判斷自己會不會遇到的數值寫出實際值；函式、欄位、設定鍵與內部機制寫在設計說明。

### 設計說明

每項改動寫成一個 `### 主題` 小標加內容，主流程在前，其餘改動在後。

```markdown
### <主題>

- **修改前**：<原本的行為>
- **修改後**：<現在的行為>
- **補充**：<其他流程與技術細節>
```

- 主題用簡短的名詞，例如「補傳範圍」「單輪限制」。
- 主題用 `###` 小標，主題之間靠小標的間距分開；粗體字的間距和內文一樣，讀者分不出哪些內容屬於同一個主題。
- 同一個主題的內容寫成一個緊密的條列，點與點之間不留空行，靠粗體標籤「修改前」「修改後」「補充」區分每點的角色。只用標準 Markdown，不用 `<br>`、縮排段落或混用條列符號排版：這些寫法在 GitLab 上的間距不穩定，手動編輯時也容易改壞。
- 行為有明確的前後對照時，開頭寫「修改前」「修改後」這兩點，寫使用者或系統看到的行為，讓讀者先看到差異再讀細節。修正 bug 時修改前寫錯誤行為。
- 補充只有一件事時寫在標籤同一行；有多件事時標籤後換行，往下縮一層，每件事一點。沒有要補充的就不寫這一點。
- 沒有前後對照的主題直接條列內容、不加標籤，不為了湊格式補上修改前、修改後：新增的行為沒有修改前、行為沒有改變的改動（例如多記一筆日誌），或修改前的行為在 diff 與既有說明裡找不到依據、只能推測時，都屬於這種情況。
- 補充寫修改前、修改後沒涵蓋的流程與技術上調整了什麼，例如查詢改成怎麼查、哪個狀態改由哪個流程標記；已經寫在修改前、修改後的內容不重複。讀者只看這個主題就要知道調整了什麼；只寫「查詢改寫，效能提升」看不出改了什麼。
- 數值、錯誤碼、設定鍵與狀態值直接寫在所屬的主題裡，不另外整理成對照清單。
- 只寫調整了什麼；選擇這個做法的原因與捨棄的替代方案不列，reviewer 有疑問時在討論串回答。
- 同一個流程、佇列或狀態全文用同一個名稱。

流程或架構有變動，而且看圖比讀文字快時，在該項改動之後附圖：分支改變多個步驟的流程、狀態轉換，或元件間的呼叫順序與相依關係。只增減一兩個步驟、改判斷條件或改單一元件內部做法時，文字就說得清楚，不畫。

- 流程或狀態轉換的變動用流程圖；模組、服務或元件的邊界、相依關係或資料流向的變動用架構圖；兩者都改就兩種都附。
- 用 Mermaid（GitHub 與 GitLab 都會渲染），每種圖分「修改前」與「修改後」各一張，只畫有變動的範圍，節點只寫步驟或元件名稱；新增的流程或元件在修改前寫「無」。

### 已知限制與可能異常

每點寫成 `**情境**：發生時使用者或系統看到什麼`，有處理方式時一併寫出，例如告警後人工對帳。

- 修改後仍會出問題的情境與觸發條件。
- 其他系統沒有配合時會出現的異常。
- 尚未在真實環境驗證的範圍：寫出哪些行為沒有實測、需要什麼環境才能驗證。已通過的測試與審查過程不寫。

部署順序、DDL、設定變更等上線步驟由上線文件記錄，不寫進內文。

## 建立

使用者要求發起 PR／MR 即代表同意建立，直接建立，不先給草稿確認。

內文以 UTF-8 寫入暫存檔再交給 CLI，避免 shell 跳脫破壞 Markdown。Windows PowerShell 5.1 的 `Set-Content`、`Out-File` 未指定編碼時中文會變成亂碼，需加上 `-Encoding utf8`。

| 平台 | 新建 | 分支已有 PR／MR |
| --- | --- | --- |
| GitHub | `gh pr create --base <base> --title "<標題>" --body-file <檔案>` | `gh pr edit --title "<標題>" --body-file <檔案>` |
| GitLab | `glab mr create --target-branch <base> --title "<標題>" --description-file <檔案>` | `glab mr update --title "<標題>" --description-file <檔案>` |

- 平台以 `git remote -v` 的主機判斷。自架 GitLab 用 `glab`，主機需已登入（`glab auth status --hostname <主機>`）；`glab mr` 系列從目前 repo 的 remote 判斷主機，不接受 `--hostname`。
- 建立前查目標分支是否已有內容重疊的開啟中 PR／MR（`gh pr list`、`glab mr list`）。有重疊時在內文寫明並告知使用者；除非使用者要求，不關閉或留言於既有的 PR／MR。
- 分支已有 PR／MR 時，每次 push 前後都對照 `git diff origin/<base>...HEAD` 的最終結果，確認標題與內文是否仍符合；有出入就依上述規範更新（`gh pr edit`、`glab mr update`），沒有出入也告知使用者已確認。
- 審查者、指派人與標籤會通知他人，使用者要求才設定。
- 建立後確認 PR／MR 的 commit 列表與預期一致，強制推送改寫歷史後同樣確認：GitHub 用 `gh pr view <編號> --json commits`，GitLab 用 `glab api "projects/<URL 編碼的 namespace/repo>/merge_requests/<編號>/commits"`。

沒有對應 CLI 或尚未登入時，輸出標題與內文讓使用者自行貼上。

## 範例

以下為示意，長度依修改範圍調整。標題只放在 `--title`，不寫進內文。

### 修正多個問題

標題：

```text
fix(sync): 排隊逾時的請求中止本文讀取並關閉連線
```

內文：

```markdown
## 摘要

修正同步路由（注單、洗分紀錄）在同一商戶高併發時，排隊逾時的請求收不到回應的問題。

同一條連線的下一個請求也不再被誤判為錯誤。

## 問題背景

1. 同一商戶同時送出超過 20 個同步請求時，多出來的請求要排隊，最多等 15 秒。
2. 排隊期間，注單批次很大或網路很慢的請求還在上傳資料。
3. 等滿 15 秒後，server 回覆逾時錯誤，client 重送同一批資料。

## 設計說明

### 排隊逾時的回應

- **修改前**：本文送得慢的請求排隊滿 15 秒後，client 一直收不到回應。
- **修改後**：排隊滿 15 秒立即收到內部錯誤，client 用同一個 `batchID` 重送。
- **補充**：排隊逾時時對連線設 `SetReadDeadline`，讓阻塞中的本文讀取立即返回；HTTP server 只設 `ReadHeaderTimeout`，本文讀取原本沒有期限。

### 逾時後的連線

- **修改前**：逾時請求沒送完的本文超過 256 KiB 時，同一條連線的下一個請求收到 400。
- **修改後**：逾時的請求關閉連線，client 開新連線重送，下一個請求不受影響。
- **補充**：
  - 逾時回應加上 `Connection: close`，不排空剩餘本文（上限 32 MiB）。
  - 連線原本會被重用，沒讀完的位元組被當成下一個請求的開頭。

### 排隊逾時的日誌

- 逾時日誌加上商戶代號與已等待的秒數。
```

### 修正單一問題

標題：

```text
fix(login): 帳號含前後空白時仍可登入
```

內文：

```markdown
## 摘要

修正從其他地方複製帳號貼上登入時，被判定為帳號不存在的問題。

## 問題背景

使用者從其他地方複製帳號貼到登入表單時，帳號前後常帶入空白。
```

### 新功能

標題：

```text
feat(login): 新增記住帳號選項
```

內文：

```markdown
## 摘要

登入表單新增「記住帳號」選項：勾選後登入成功，下次開啟登入頁自動帶入帳號，不必每次重新輸入；取消勾選後不再帶入。

## 已知限制與可能異常

- **共用裝置**：帳號存在瀏覽器的 `localStorage`，共用電腦上的下一位使用者會看到上一位的帳號，櫃檯等共用裝置不要勾選。
```
