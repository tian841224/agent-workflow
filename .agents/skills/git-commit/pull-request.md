# PR／MR 規範

本文件規範 PR／MR 的標題、內文與建立方式。類型表與「內容只描述這次修改」依 [SKILL.md](SKILL.md)；push 的授權依入口文件的硬護欄。

## 內容來源

以遠端目標分支（例如 `origin/main`）與 HEAD 的差異為準，避免本機分支過期而把已合併的 commit 算進來。未指定目標分支時用 remote 的預設分支。

- 內容以 `git diff origin/<base>...HEAD` 的最終結果為準；`git log origin/<base>..HEAD` 的 commit 訊息只作為線索，分支中途加入後又改掉或移除的內容不寫。
- 工作樹中未 commit 的修改不會進入 PR／MR，不寫進內文；有這類修改時先告知使用者。

## 標題

```text
<類型>(<模組>): <大綱>
```

- 類型：依整個分支的主要變化，從 SKILL.md 的類型表選一個。
- 模組：整個分支只動到單一模組時才加；跨模組時寫成 `<類型>: <大綱>`。
- 大綱：一句話列出最主要的 2～3 項變化，結尾不加句號。

## 內文

內文讓 reviewer 讀 diff 前先知道三件事：這個分支改變了什麼行為、為什麼這樣做、上線要注意什麼。diff 看得到的內容（改了哪些檔案、函式、欄位、測試與文件）不另外列出；函式、欄位或錯誤碼的名稱只在說明行為、決策或相容性時帶出。

| 段落 | 何時寫 | 寫什麼 |
| --- | --- | --- |
| 摘要 | 一律 | 改了哪些功能或業務邏輯 |
| 問題背景 | 修正 bug | 問題在什麼情境下發生 |
| 修改前後差異 | 使用者或系統看到的行為有改變 | 每項改變在修改前後的行為，可附圖 |
| 設計說明 | 有讀 diff 看不出原因的決策 | 決策與原因 |
| 上線與相容性 | 有部署、相容性、限制或尚未驗證的範圍要注意 | 要注意的事與處理方式 |

依表格順序排列，不符合「何時寫」的段落整段省略，不留空標題。重構或純文件修改通常只有摘要，有不明顯的決策時再加設計說明。

### 摘要

一兩句話，從使用者或系統行為的角度說明這個分支改了哪些功能或業務邏輯，以及目的；修正 bug 時說明使用者在什麼情境下遇到什麼症狀。函式、判斷條件、設定值等實作細節不寫進摘要。

### 問題背景

依觸發順序列出造成問題的條件與步驟。併發上限、等待秒數、大小上限等觸發條件寫出實際值，讓讀者能判斷自己的情境是否會遇到。

### 修改前後差異

每項改變一點，寫成 `**項目名稱**`，下面分「修改前」與「修改後」兩行，寫使用者或系統看到的行為。

- 修正 bug：修改前寫錯誤行為；有重現結果時直接寫結果，例如「慢速 client 收不到逾時回應」。
- 新增功能：修改前寫使用者原本怎麼做或遇到什麼，例如「每次登入都要重新輸入帳號」，不寫「無」。
- 上限、逾時、錯誤碼等數值會影響看到的行為時，寫出實際值。
- 同一個佇列、錯誤碼或設定鍵全文用同一個名稱。

流程或架構有變動，而且看圖比讀文字快時，在條列之後附圖：分支改變多個步驟的流程、狀態轉換，或元件間的呼叫順序與相依關係。只增減一兩個步驟、改判斷條件或改單一元件內部做法時，條列就說得清楚，不畫。

- 流程或狀態轉換的變動用流程圖；模組、服務或元件的邊界、相依關係或資料流向的變動用架構圖；兩者都改就兩種都附。
- 用 Mermaid（GitHub 與 GitLab 都會渲染），每種圖分「修改前」與「修改後」各一張，只畫有變動的範圍，節點只寫步驟或元件名稱；新增的流程或元件在修改前寫「無」。

### 設計說明

寫 reviewer 讀 diff 時可能會問「為什麼不直接⋯⋯」的地方：選擇這個做法的限制條件、捨棄的替代方案、不明顯的正確性依據。每點寫成 `**決策**：原因`；做法本身 diff 看得到，只帶一句讓讀者知道在說哪段程式。

### 上線與相容性

每點一兩句，寫出要做的事或影響範圍，以及處理方式：

- 部署順序、DDL、資料回填或設定變更；步驟很多時指向上線文件的路徑。
- 破壞性的 API 或資料格式變更，以及需要配合修改的系統。
- 需要其他系統調整的設定，例如上游的逾時。
- 已知限制與觸發條件。
- 尚未在真實環境驗證的範圍：寫出哪些行為沒有實測、需要什麼環境才能驗證。已通過的測試與審查過程不寫。

## 建立

使用者要求發起 PR／MR 即代表同意建立，直接建立，不先給草稿確認。

內文以 UTF-8 寫入暫存檔再交給 CLI，避免 shell 跳脫破壞 Markdown。Windows PowerShell 5.1 的 `Set-Content`、`Out-File` 未指定編碼時中文會變成亂碼，需加上 `-Encoding utf8`。

| 平台 | 新建 | 分支已有 PR／MR |
| --- | --- | --- |
| GitHub | `gh pr create --base <base> --title "<標題>" --body-file <檔案>` | `gh pr edit --title "<標題>" --body-file <檔案>` |
| GitLab | `glab mr create --target-branch <base> --title "<標題>" --description-file <檔案>` | `glab mr update --title "<標題>" --description-file <檔案>` |

- 平台以 `git remote -v` 的主機判斷。自架 GitLab 用 `glab`，主機需已登入（`glab auth status --hostname <主機>`）；`glab mr` 系列從目前 repo 的 remote 判斷主機，不接受 `--hostname`。
- 建立前查目標分支是否已有內容重疊的開啟中 PR／MR（`gh pr list`、`glab mr list`）。有重疊時在內文寫明並告知使用者；除非使用者要求，不關閉或留言於既有的 PR／MR。
- 分支已有 PR／MR 時，每次 push 前後都對照 `git diff origin/<base>...HEAD` 的最終結果，確認標題與內文是否仍符合；有出入就依上述規範更新（`gh pr edit`、`glab mr update`），沒有出入也告知使用者已確認。
- 審查者、指派人與標籤會通知他人，使用者要求才設定。
- 建立後確認 PR／MR 的 commit 列表與預期一致，強制推送改寫歷史後同樣確認：GitHub 用 `gh pr view <編號> --json commits`，GitLab 用 `glab api "projects/<URL 編碼的 namespace/repo>/merge_requests/<編號>/commits"`。

沒有對應 CLI 或尚未登入時，輸出標題與內文讓使用者自行貼上。

## 範例

以下為示意，長度依修改範圍調整。標題只放在 `--title`，不寫進內文。

### 修正多個問題

標題：

```text
fix(sync): 排隊逾時的請求中止本文讀取並關閉連線
```

內文：

```markdown
## 摘要

修正同步路由（Wager、Balance Event sync）在同一商戶高併發時，排隊逾時的請求收不到回應，以及同一條連線的下一個請求被誤判為錯誤的問題。

## 問題背景

1. 同一商戶同時進入同步路由的請求超過 20 個時，其餘請求排隊，最多等 15 秒。
2. 排隊中的請求，client 可能還在送本文（上限 32 MiB，一批注單很大或網路很慢）。
3. 排滿 15 秒後，server 回內部錯誤，client 用同一個 `batchID` 重送。

## 修改前後差異

- **慢速本文收不到回應**
  - 修改前：本文送得慢的請求排隊逾時後，client 一直收不到回應。
  - 修改後：排隊逾時後立即收到內部錯誤，client 用同一個 `batchID` 重送。
- **下一個請求收到 400**
  - 修改前：逾時請求沒送完的本文超過 256 KiB 時，同一條連線的下一個請求收到 400。
  - 修改後：逾時的請求關閉連線，client 開新連線重送，下一個請求不受影響。

## 設計說明

- **用 `SetReadDeadline` 中止本文讀取**：HTTP server 只設 `ReadHeaderTimeout`，排隊中的請求沒有其他方式讓阻塞中的本文讀取返回。
- **逾時後關閉連線，不排空剩餘本文**：排空要繼續等慢速 client 送完最多 32 MiB；而剩餘本文超過 256 KiB 時，`MaxBytesReader` 包住 `Request.Body`，`net/http` 看不出本文沒讀完而重用連線，剩下的位元組會被當成下一個請求的開頭。
```

### 修正單一問題

標題：

```text
fix(login): 帳號含前後空白時仍可登入
```

內文：

```markdown
## 摘要

修正從其他地方複製帳號貼上登入時，被判定為帳號不存在的問題。

## 問題背景

使用者從其他地方複製帳號貼到登入表單時，帳號前後常帶入空白。

## 修改前後差異

- **帳號前後空白**
  - 修改前：顯示帳號不存在，無法登入。
  - 修改後：可以正常登入。
```

### 新功能

標題：

```text
feat(login): 新增記住帳號選項
```

內文：

```markdown
## 摘要

登入表單新增「記住帳號」選項，讓常用裝置不必每次重新輸入帳號。

## 修改前後差異

- **記住帳號**
  - 修改前：每次開啟登入頁都要重新輸入帳號。
  - 修改後：勾選後登入成功，下次開啟登入頁自動帶入帳號；取消勾選後不再帶入。

## 上線與相容性

- **共用裝置**：帳號存在瀏覽器的 `localStorage`，共用電腦上的下一位使用者會看到上一位的帳號，櫃檯等共用裝置不要勾選。
```
