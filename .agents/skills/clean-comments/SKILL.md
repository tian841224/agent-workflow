# 精簡與結構化程式碼註解規範

| 註解類型 | 放置位置 | 核心職責 | 長度上限 |
| :--- | :--- | :--- | :--- |
| **函式註解** | 函式／介面宣告正上方 | 站在呼叫端視角說明功能目的與核心合約，**不劇透內部分支與實作細節** | 1–2 句 |
| **流程註解** | 關鍵 `if` 分支、降級邏輯、演算法正上方 | 說明**為什麼這樣做**或非顯而易見的業務意圖，不翻譯程式碼在做什麼 | 1 句 |

Go 等有慣例的語言，函式註解以函式名稱開頭（例如 `// CheckLargeOutAndPrecheck 檢查是否超過大額洗分門檻並向 GameFacing 進行預檢。`）。

## 範例對照

```go
// 錯誤：全堆在函式上方、混雜內部實作
// CheckLargeOutAndPrecheck 洗分金額超過本機 balanceOutLimit 門檻時，
// 出款前呼叫 Large out precheck 確認 Session/Machine 有效。
// sessionUsecase 未 wire（GameFacing 未啟用或初始化尚未完成）時安全 no-op，允許出款。
func CheckLargeOutAndPrecheck(machineID string, expectedAmount float64, routeName string) (allowPayout bool, errMsg string, err error) {
    if sessionUsecase == nil {
        return true, "", nil
    }
    return (*sessionUsecase).CheckLargeOutAndPrecheck(machineID, expectedAmount, routeName)
}

// 正確：職責分離、就近說明
// CheckLargeOutAndPrecheck 檢查是否超過大額洗分門檻並向 GameFacing 進行預檢。
func CheckLargeOutAndPrecheck(machineID string, expectedAmount float64, routeName string) (allowPayout bool, errMsg string, err error) {
    // 模組未啟用或未初始化時安全跳過，允許正常出款
    if sessionUsecase == nil {
        return true, "", nil
    }
    return (*sessionUsecase).CheckLargeOutAndPrecheck(machineID, expectedAmount, routeName)
}
```

## 條件與依據要能對得上程式碼

註解一旦描述「什麼情況下」「依據什麼事實」，就必須跟程式碼與現實逐字對得上，寫錯比不寫更糟——不寫只是沒資訊，寫錯是主動誤導。

- **條件要跟判斷式對齊**：註解講的觸發情境，範圍必須與底下的 `if`／`switch` 完全一致，不能比程式碼窄（漏掉它其實也涵蓋的情況）或寬（暗示它排除了其實還在處理的情況）。條件之後被改寬或改窄時，同一行的註解要跟著更新，否則會變成「這裡以前只處理 A，註解沒改，現在其實 A、B 都處理，讀者以為 B 走的是別的邏輯」。
- **判斷依據要寫成可查證的事實，不要寫成聽起來合理的分類詞**：「視為連線或閘道異常」這種話任何情境都能套用，等於沒有排除其他可能性；換成「這個系統的錯誤一律回 200，非 2xx 只可能來自這條路徑本身」，才是能被程式碼或文件驗證、也才會在事實不成立時被人發現有問題的說法。寫不出具體依據，代表這個判斷本身還沒想清楚，不是註解的問題。
- **依據若只是假設、尚未證實，要標注出來**：`// 假設 X 一定會回傳 Y（尚未跟對方確認）` 比讓人誤以為是已驗證的事實安全得多——這決定了未來出錯時，第一個該懷疑的是不是這則假設。

高風險路徑（金流、對外契約、不可逆的降級／關閉操作）上的判斷依據註解可以超過 1 句，把支撐這個判斷的具體事實、其查證狀態、以及誤判的後果一併寫出來；其餘情況仍維持 1 句，不要把這個例外當常態。

## 完整流程或跨函式邏輯寫文件，不寫成註解

需要說明的是「一整條流程怎麼走」「這個機制的完整設計」，而不是單一判斷式旁的一句話時，該寫的是文件，不是把說明硬塞進註解：

- **判斷依據**：內容涉及多個分支、多個函式或跨模組的先後順序，或需要畫表格、列情境對照，已經超出「這個判斷為什麼這樣做」的範圍，變成「這整套機制是怎麼運作的」。
- **為什麼不能寫成註解**：這類內容一旦寫進註解，要嘛擠成函式上方一大段違反「函式註解只講對外目的」的說明，要嘛拆成好幾行分散在各個判斷式旁、讀者要跳好幾個地方才拼得出全貌；而且程式改了，這種分散的說明比單一判斷式旁的一句話更容易顧此失彼、局部更新而整體失準。
- **該怎麼做**：本專案用 `project-docs` skill 管理的 `docs/flows/<slug>.md`（跨模組流程）與 `docs/modules/<slug>.md`（單一模組的內部流程、共用狀態、假設與坑）承接這類內容；程式碼裡改回 1 句的目的性註解，或在關鍵分支點加 1 句指向文件的線索（例如「推翻判定的完整規則見 docs/xxx.md」），不要在註解裡重複文件已經寫的東西。

## 撰寫禁忌

1. **不翻譯語法**：`// 如果 err 不等於 nil，返回錯誤` 這類註解沒有資訊量；程式碼本身就自解釋。
2. **不寫內部步驟流水帳**：不在函式上方列 `步驟1：驗證參數；步驟2：打API...`；拆分成可讀性高的子函式，或在關鍵步驟上方各寫 1 句。
3. **不過度註解顯而易見的命名**：`var userID string // 使用者 ID` 這類註解該刪——良好命名本身就是最佳註解。
4. **改既有註解時不做零資訊量的措辭調整**：新舊版本只是換句話說、沒有新增判斷依據、新邊界情況或新後果時，就不要動——維持原文，或者不改。這種「有改但沒有新資訊」的變更，會讓混在同一次改動裡的真正邏輯異動被誤判成「這裡只是潤飾過」而略過，之後想追查某個行為是何時、為何改變的，也會被這些沒有實質內容的版本擋在中間。

## 自我檢查

- [ ] 函式上方的 doc 是否只有對外的目的說明？
- [ ] 邊界判斷／降級處理是否移到該邏輯正上方，而不是堆在函式頂端？
- [ ] 這則註解講的條件／範圍，是否與底下程式碼的實際判斷式逐字對得上？判斷式改過的話，註解是否也跟著改了？
- [ ] 判斷依據是不是具體、可查證的事實？如果只是聽起來合理的分類詞，能不能換成真正的依據，或標成尚未查證的假設？
- [ ] 這次是新增註解、修內容，還是只是換句話說？只是換句話說的話，改了會不會反而製造「這裡有實質變動」的錯覺？
- [ ] 想寫的內容是不是「整條流程」或「跨函式的完整機制」？是的話該建文件，註解只留 1 句指向文件或講這個判斷式本身的理由。
