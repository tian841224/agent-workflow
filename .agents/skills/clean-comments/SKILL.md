# 精簡與結構化程式碼註解規範

編輯觸發條件以入口文件的「程式碼註解」節為準；一般簡短註解使用該處的基本原則。Repo 的入口是 `AGENTS.md`；安裝後共用入口是 `~/.agents/AGENTS.md`，平台入口為 `CLAUDE.md`／`AGENTS.md`／`GEMINI.md`。

<!-- enforcement:start -->
先確保事實正確、契約與風險資訊完整，再精簡文字。下表的長度是一般建議，不是刪除必要資訊的上限；高風險路徑（金流、對外契約、不可逆的降級／關閉操作）可用多句或多行，保留支撐判斷的具體事實、查證狀態與誤判後果。

| 註解類型 | 放置位置 | 核心職責 | 一般長度 |
| :--- | :--- | :--- | :--- |
| **函式註解** | 函式／介面宣告正上方 | 站在呼叫端視角說明功能目的與核心合約 | 1–2 句 |
| **流程註解** | 關鍵 `if` 分支、降級邏輯、演算法正上方 | 說明**為什麼這樣做**或非顯而易見的業務意圖 | 1 句 |
| **宣告註解** | 欄位、型別、常數正上方或右側 | 補充非顯而易見的單位（如 ms、千分比）、格式約束或邊界 | 1 句／片語 |

Go 等有慣例的語言，函式註解以函式名稱開頭。

## 規則

1. 函式／介面註解說明呼叫端需要知道的契約，包含會影響回傳值、錯誤或副作用的降級行為；分支的局部判斷依據與原因放在該邏輯正上方。不能因為降級發生在內部，就把呼叫端需要的資訊全部移走。
2. 條件敘述涵蓋的範圍要與底下的 `if`／`switch` 一致，用詞可不同、可補充原因，但不得比判斷式寬或窄；判斷式改寬或改窄時，同一行的註解跟著改。
3. 判斷依據寫成可查證的事實；尚未證實的假設明確標示查證狀態。程式碼只能證明發生了什麼時，就寫可觀察行為與限制，不把推測的原因或「安全」保證寫成事實。
4. 既有註解若仍正確、資訊足夠且位置合適，就保留；只修正具體缺陷或依據、邊界、後果、對應程式行為的變化。明確要求的註解整理依指定範圍處理，避免混入無關潤飾。
5. 完整流程或跨函式機制寫進 `docs/flows/<slug>.md` 或 `docs/modules/<slug>.md`（依 [project-docs](../project-docs/SKILL.md)）；程式碼保留目的或文件線索，以及理解當地契約與風險所需的資訊。
6. 不寫歷程描述：註解只描述目前的完整職責與契約，不寫相對於舊版的敘述（「原本」「改為」「不再」「已移除」「修正了」這類措辭與追加修改的流水帳）；修改歷程寫進 commit message 或 PR 說明，歷史由 Git 保存。
7. 移除語法翻譯、命名複述與被註解掉的廢棄程式碼。
8. TODO／FIXME 寫明可執行的觸發條件、依賴任務或驗證標準。
