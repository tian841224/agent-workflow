# lite 軌（LT1–LT4，重軌等級任務的單對話單人模式）

適用：**僅使用者主動指定**（如「走 lite」）才啟用，不自動判入；判軌命中重軌判準時預設仍走多角色重軌。定位是「用標準軌的骨架跑重軌等級的任務」：規格、方案、實作由主對話一人直接完成，不 spawn PM／architect，單檔 mini-spec 取代 spec／checklist／plan 三檔；把關交獨立唯讀 reviewer→qa 序列 spawn（同重軌 R4→R5），「審查者與驗收者不是實作者」原則不變；卡關例外轉 debugger（唯讀）。機械性唯讀查證（grep 呼叫點、讀檔彙整、影響面調查）可隨時 fan-out 唯讀 agent，**一律指定最低階模型**（Claude Code：model haiku），只回傳結論、不佔主對話 context。單人寫規格（砍掉 PM↔architect 往返）的盲點由三道機制補償：規格自審紀律（見下）、獨立 reviewer／qa 把關、qa 探索性測試。

```
LT1 定調與凍結（單一確認點）：先讀專案既有文件與現況行為當 baseline（含記憶層
    overview.md；影響面調查可平行 fan-out 唯讀 agent 查呼叫點與契約現況，結論附進導讀）
    → 依任務性質判定模式並宣告理由（使用者可否決；判斷不出走功能模式）：
    ・修正模式（全部成立才可）：純程式碼修正（bug fix／重構／效能／內部結構），
      不新增使用者可觀察行為；不動對外契約（API／WS／DB schema／前端畫面）；
      預期正確行為已明確 → 以架構師視角分析現況架構與根因、候選做法 trade-off
      （解法明顯唯一時說明理由後單方案徑行），並做六大面向設計自審（面向定義見
      agents/reviewer.md，不複述；依改動性質挑選相關面向逐項評估、無關面向一句話
      帶過；保底：涉及寫入路徑或外部輸入時，資料一致性與資安不得略）
    ・功能模式（其餘一律）：先列商業規格（做法同重軌 R1）——目標／非目標、條目化
      規格含 G-W-T 與輸入輸出邊界錯誤定義；開放問題清空、不得用「照既有行為 1:1」
      自答；技術風險寫進導讀交使用者裁決，不得自行吸收
    → 兩模式收斂：用 templates/mini-spec.md 定完成條件與測試條件——A<n> 驗收條目
      （G-W-T＋test-type＋cmd/expect，前端條目 type: ui＋steps/expect；涵蓋邊界值／
      等價類／異常路徑各至少一條，不只 happy path，不適用需註明理由；條數不受
      標準軌 3–6 條限制，約 12 條以上建議拆任務或改走完整重軌）＋凍結前過
      規格自審紀律（見下）
    → 分析結論＋導讀一次送使用者：釐清、選方案、凍結一次完成（frozen: 填日期）；
      凍結後除非發現條目與現實衝突（停手交使用者確認），不得中途修改條件
LT2 實作：依凍結 seam red→green 一次一個切片，對照條目自檢（不 commit）；寫入
    一律主對話單人、不拆平行；唯讀支援工作（查呼叫點、跑分析）可隨時 fan-out
    （最低階模型）
LT3 把關與驗收（獨立唯讀、序列 reviewer→qa）：pre-review 通過（跳過語言檢查時
    先人工補跑 build/test）→ spawn reviewer 審 diff 對照 mini-spec.md（六大面向
    依改動性質裁量，≤2 輪；交接 prompt 依 handoff.md 裁剪，不夾帶實作者自評），
    blocker 打回主對話修正、修正 diff 重過 pre-review＋複審 → reviewer 通過後
    spawn qa：逐條 cmd/expect 判定 PASS/FAIL＋探索性測試（規則同標準軌 M4）；
    FAIL 彙總一批打回主對話修正 → 修正 diff 過 pre-review＋reviewer 輕量複審，
    qa 只重驗 FAIL 與波及條目 → 同一條目累計 3 次仍失敗轉 debugger
LT4 收尾：回報使用者（改了什麼、驗收結果、複驗方式、流程統計——審查輪數、打回
```

## 規格自審紀律（LT1 凍結前必過——單人寫規格的防走過場條款，缺一視為未過 LT1）

這是砍掉「architect 審 PM 規格」往返後的對價：

1. **凍結即題目**：完成條件與測試條件在實作前定案，實作後不得改條目遷就實作；發現衝突停手交使用者裁決，不得先改題再交卷。
2. **機械防線強制**：pre-review 未過不得進審查；stop-check hook 把關凍結與未勾條目——僅存的非自律防線，地位為強制而非輔助。
3. **證據硬規則**：修正模式的面向結論，與兩模式共同檢核——可測性（每條 A\<n\> 落得到可執行的 cmd/expect 或 ui steps、環境前置條件具備）與影響面（受影響模組與呼叫點清單、既有契約／schema 的變動範圍與向後相容性）——必附實際讀檔／grep 證據；無證據不得標通過，結論隨導讀一併給使用者查驗。

## 文件與邊界

任務目錄同標準軌單檔：`~/.claude/projects/<project-slug>/acceptance/<task-slug>/mini-spec.md`（stop-check hook 自動把關凍結與未勾條目；分析結論摘要寫入模板「設計分析」選填段，供中斷續作回復脈絡）。凍結後增刪與輕量修訂循 `workflow/acceptance-spec.md` 凍結原則（需求變更回 LT1 重出）；回合上限見 SKILL.md，計數口頭列在回報中。升軌訊號：規格反覆翻案、影響面比自審認定的大、規模大到需要平行寫入、修正模式途中發現須動對外契約或定義新行為（最少退回 LT1 換功能模式重新凍結）、把關循環超限且使用者裁決後仍不收斂 → 停手建議轉完整重軌，補齊該軌前置步驟再繼續。LT3 本就序列，各平台一致；Codex／Antigravity 單進程無法 fan-out，唯讀查證退化為主對話自己查，reviewer／qa 切換身分照常宣告。
