# What a Good Test Looks Like

## Behavior, not implementation

A test names a capability, not a code path. If you can rename every internal function and variable in the implementation without touching the test, the test is at the right altitude.

```
// Good — reads as a spec, survives refactors
test("user can checkout with a valid cart", () => { ... })
test("checkout is rejected when the cart is empty", () => { ... })

// Bad — names the internal call, breaks the moment you rename it
test("calls validateCart() then calls chargeCard()", () => { ... })
```

## Independent expected values

The expected value in an assertion must come from somewhere other than re-running the code's own logic by hand.

```
// Bad — tautological. If add() has a bug, this test has the same bug.
expect(add(2, 3)).toBe(2 + 3)

// Good — expected value is a known-good literal from the spec/worked example
expect(add(2, 3)).toBe(5)
```

The same trap applies to snapshots: a snapshot generated by running the code once and accepted as "correct" is not independent — it only proves the code is consistent with itself, not that it's right. Prefer literal expected values for anything with a knowable correct answer; reserve snapshots for cases where the shape of output matters more than a specific value, and review new snapshots by hand before accepting them.

## Structure: Arrange / Act / Assert

Keep the three phases visually distinct so the reader can tell what's setup, what's the behavior under test, and what's being checked.

```
test("checkout is rejected when the cart is empty", () => {
  // Arrange
  const cart = createEmptyCart()

  // Act
  const result = checkout(cart)

  // Assert
  expect(result.ok).toBe(false)
  expect(result.error).toBe("EMPTY_CART")
})
```

## One behavior per test

A test that asserts multiple unrelated things fails ambiguously — you can't tell which behavior broke without reading the diff. Split by behavior, not by function under test:

```
// Bad — two behaviors bundled into one test
test("checkout", () => {
  expect(checkout(validCart).ok).toBe(true)
  expect(checkout(emptyCart).ok).toBe(false)
  expect(checkout(expiredCoupon).error).toBe("COUPON_EXPIRED")
})

// Good — one behavior, one test, one failure reason
test("checkout succeeds with a valid cart", () => { ... })
test("checkout is rejected when the cart is empty", () => { ... })
test("checkout is rejected when the coupon is expired", () => { ... })
```

## Vertical slices, not horizontal layers

Write one test, make it pass, then write the next — don't write a whole suite of imagined tests before any implementation exists. Each test should be a **tracer bullet**: it tells you something you didn't know before you wrote it (does this edge case matter? what should the error look like?), and the next test you write should be informed by what the last cycle taught you, not by a pre-drawn list of "all the cases I can think of right now."

## Naming

Name the test after the observable outcome, phrased so a non-reader of the implementation understands what capability is being verified:

- `<subject> <does/can/cannot> <behavior> [when <condition>]`
- e.g. `"order total includes tax when shipping address is set"`, not `"test calculateTotal 3"`

## Checklist before you write an assertion

- [ ] Does this test go through a pre-agreed seam (see SKILL.md § Seams), not an internal?
- [ ] Is the expected value independent of the implementation's own logic?
- [ ] Does the test name describe a capability, not a function call sequence?
- [ ] Does this test check exactly one behavior?
- [ ] Would this test still pass after a pure refactor that doesn't change behavior?
- [ ] Would this test still fail if the behavior it names were broken?
