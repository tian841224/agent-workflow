# 自我學習迴圈 (Self-Learning Loop) — 全域

跨所有專案的自我學習機制：任務中擷取教訓 → 蒸餾成精煉記憶 → 升級為規則／技能／決策紀錄 → 定期修剪與驗證。本檔為**權威定義**，各專案的 learning 規則只做專案特化補充、不重複本檔內容。架構參考〈AI Agent 7 層架構〉(<https://raymondhouch.com/lifehacker/digital-workflow/ai-agent-7-layer-architecture/>)。

## 0. 每個 session 開場

- 若 `~/.claude/memory/MEMORY.md`（全域通用記憶）存在，**先讀取**再開始任務——這是跨專案的「便利貼」層。
- Claude Code 已自動注入當前專案的 per-project 記憶（`~/.claude/projects/<專案>/memory/`）；不必再手動讀。
- 兩層記憶都是「當下觀察」，引用前需確認仍成立（見 §7）。

## 1. 迴圈總覽

```text
擷取 (Capture) → 蒸餾 (Distill) → 升級 (Promote) → 修剪 (Prune) → 驗證 (Verify) ─┐
   ▲                                                                            │
   └────────────────────────────────────────────────────────────────────────────┘
```

- **擷取**：任務中即時把教訓丟進 inbox，成本低、不打斷任務。
- **蒸餾**：`learn`／`evolve` skill 把 inbox 整理成 MEMORY 精煉條目（去重、概括）。
- **升級**：重複出現或結構性的教訓，升級成規則／技能／決策紀錄，成為永久行為。
- **修剪**：刪除過時、被證偽、已升級的條目，維持便利貼層精簡。
- **驗證**：檢查既有教訓是否真的阻止了重複錯誤；無效教訓必須改寫或升級，不得原樣留著。

## 2. 擷取觸發（always_on）

任務進行中遇到下列任一情況，**必須在該任務結束前**把教訓寫入對應 inbox（§4 分流、§5 格式）：

1. 使用者糾正了你的做法、答案或假設。
2. 出現編譯／測試／執行錯誤，且根因是可概括的錯誤假設（而非一次性筆誤）。
3. 發現實際行為與文件／規則的描述不符。
4. 同一 session 內第二次犯同類錯誤。
5. 使用者明說「記住」「記錄教訓」「下次注意」（此時改用 `learn` skill 完整處理）。

**例外**：教訓若屬方案取捨的設計決策，且該專案有決策紀錄機制（如 ADR／`docs/decisions/`），直接走該機制；inbox 只記一行指回該決策，不重複內容。

## 3. 記憶分層與分流

| 教訓性質 | 去向（記憶層） |
|---|---|
| **跨專案通用**：協作偏好、工具鏈陷阱、通用流程與方法論 | 全域 `~/.claude/memory/`（inbox.md → MEMORY.md） |
| **專案特定**，且該專案有 repo 內記憶層（如 `.agent/learning/`） | 該專案 repo 內記憶層（跨 agent、進版控優先） |
| **專案特定**，該專案無 repo 內記憶層 | Claude Code 內建 per-project 記憶（`~/.claude/projects/<專案>/memory/`，用 `consolidate-memory` skill 維護） |

判斷原則：**這條教訓換一個專案還成立嗎？** 成立→全域；只在此專案成立→專案層。拿不準時先進全域 inbox，`evolve` 時再定位。

**技術性教訓（工程踩坑／設計模式）不另開系統**：像「Redis 寫入忘了設 TTL」「cache 多入口沒同步失效」這類技術踩坑，本質上也是「專案特定」或「跨專案通用」教訓的一種，一樣走上表分流，不建立獨立的 knowledge base。差別只在於：technical 類教訓在 MEMORY 條目裡應標註涉及的技術/模組（方便日後同類問題搜尋），見 §4.2 的「技術 playbook」升級路徑。

## 4. 蒸餾／升級／修剪規則

### 4.1 蒸餾（inbox → MEMORY）

- 觸發：使用者執行 `learn`／`evolve`；或任務結束時某 inbox 未處理條目 ≥5。
- 每條改寫為「可操作的一句話＋適用時機」，合併重複條目，保留來源與日期。
- 各 MEMORY 檔上限 **50 條**；達上限時必須先修剪或升級，禁止無限成長。

### 4.2 升級（MEMORY → 規則／技能／決策紀錄）

| 教訓性質 | 去向 |
|---|---|
| 每個任務都該遵守的準則，或同類教訓重複 ≥2 次 | 規則檔：跨專案→`~/.claude/rules/`；專案內→該專案規則（如 `.agent/rules/`） |
| 多步驟可重複的程序（「如何做某件事」） | 新增／更新 skill：跨專案→`~/.claude/skills/`；專案內→該專案 skills |
| 方案取捨、架構決策 | 該專案決策紀錄機制（如 ADR）；無則記在全域規則或 skill |
| 同一技術域（如 Redis、WebSocket、快取）累積 **3～5 條**技術性教訓 | 蒸餾成一份「技術 playbook」：一份文件彙整該技術域的設計決策流程 + 必過檢查清單 + 已知坑速查，放在教訓所屬的記憶層（跨專案→全域 `~/.claude/memory/`；專案特定→該專案的記憶層，同上表判斷），檔名建議 `playbook-<技術域>.md` |

升級後，MEMORY 原條目**刪除或改為一行指標**（指向新位置），避免雙重維護與內容漂移。技術 playbook 是活的：新教訓屬於某 playbook 的技術域時，同一次更新順手在該 playbook 補一列檢查項並連回來源，不要另開新條目與 playbook 內容重複。

**與 ADR 的分工**：ADR 記「為什麼這樣決定」（一次性決策的理由與被拒方案）；技術 playbook 記「下次碰到這個技術，照這個做／別踩這個坑」（可複用的操作型知識）。同一個事件可能同時觸發兩者——例如「改用 XX 快取策略」值得寫 ADR 記錄取捨理由，同時如果踩到了「快取沒設 TTL」這種技術坑，也值得累積進對應技術 playbook。

### 4.3 修剪

- `evolve` 時逐條驗證：條目引用的檔案／指令／行為是否仍存在（用讀檔工具實際確認，不憑印象）；過時或被證偽的條目直接刪除。
- 某教訓記錄後同類錯誤仍再度發生 → 該條目視為**無效**，必須升級為規則或 skill 並改寫，不得原樣保留。

## 5. 檔案格式

### 5.1 inbox 條目（append-only，蒸餾後移除）

```markdown
## YYYY-MM-DD｜類型: 糾正｜專案: <名稱或 global>｜來源: <session 主題 / commit / PR>
- 情境：一句話描述發生什麼。
- 教訓：錯誤假設是什麼、正確做法是什麼。
- 建議去向：global-MEMORY｜project-MEMORY｜rule:<檔案>｜skill:<名稱>｜decision-record
```

類型限定：`糾正`（使用者糾正）、`錯誤`（執行錯誤反思）、`發現`（行為與文件不符）、`指示`（使用者要求記住）。

### 5.2 MEMORY 條目

```markdown
- **[M-NNN]** 教訓一句話。適用：什麼情況下要想起這條。（來源: <事件>, 記錄: YYYY-MM-DD）
```

編號流水遞增、不重用；依分區歸類（協作偏好／環境與工具陷阱／流程教訓／專案事實）。

## 6. 週期回顧（`evolve` skill）

- 建議頻率：**每週一次**；或任一 inbox 未處理 ≥5 條、MEMORY 逼近上限時提前執行。
- 完整程序見 `evolve` skill；完成後更新 MEMORY 表頭的「上次蒸餾」「上次回顧」與條目數。
- 可另設排程或 hooks 提醒執行（選配增強）；本迴圈的擷取觸發（§2）為規則層，不依賴任何特定 agent 的 hook 機制。
- **無 skill 載入能力的 agent**：`learn`／`evolve` 只是操作捷徑；改為直接把本檔 §4／§5 步驟與對應 SKILL.md 當一般文件讀取後手動執行即可，迴圈本身不依賴 skill 機制。

## 7. 誠實性與安全邊界

- 記憶條目是「當下觀察」：引用前必須驗證仍成立；不確定的觀察標註「待驗證」，禁止把未驗證推論寫成事實。
- 進版控的記憶層（如專案 repo 內的 `.agent/learning/`）**禁止寫入任何秘密**（token、密碼、連線字串、個資）；環境變數只記名稱、不記值。全域 `~/.claude/memory/` 雖不進版控，同樣不記秘密值。
- 教訓與規則衝突時，以規則檔與決策紀錄為準，並在下次 `evolve` 時修正該條目。
