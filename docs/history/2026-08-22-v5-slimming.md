## Decisions and rationale（含被否決的選項）

- **保留 step-level `when` 評估，只刪 `collect_evidence` 等 legacy 機制。** 刪碼與省 token 方向相反時選省 token：55 行純函式跑在 runtime 側、agent 從不讀，卻能讓 file-scope fix 少寫 4 條 evidence step（單 task 省 1,500–5,000 tokens）。**否決「一併刪掉條件式評估」**——會讓輕任務永遠付重任務代價，而輕任務是常見情況。完整性不受影響：main mode 下主對話本來就能整個 capability 不放進 `workflow_request`，step-level gating 嚴格弱於它。
- **`dimension_waivers` 選擇刪除承諾，不是實作它。** 原設計要求 observed evidence 才能豁免 Reviewer `Architecture consistency`；`manual_plan` 下這條路徑不可達。**否決「讓它可宣告」**——那是真正的完整性損失。留著不可達等於文件說謊，所以刪除承諾本身（`SKILL.md:103-105`、`templates/task.md:121`）。
- **memory-context 改為僅 SessionStart 注入，移除 UserPromptSubmit。** **否決「保留每輪但瘦身」**——每輪成本的根源是頻率，不是體積；且 `workflow/SKILL.md` §2 本來就規定需要時由 agent 主動 `knowledge.py Search`，UserPromptSubmit 自動注入是重複機制。
- **不引入 ADR / CONTEXT.md 兩套獨立檔案格式，改由 project-docs 新增 `decision` / `glossary` doc_type 承接。** 理由：project-docs 既有的 `covers` 機制讓決策文件自動吃到 git 比較的 `stale` 標記，外掛 ADR 檔案沒有這個能力，且不必維護第二套 frontmatter／分工規則。
- **既有 in-flight legacy task 用 4 行預設相容（`workflow_request` 缺省時預設 `[reviewer, verifier]` + 條件式 `adversarial`），不寫 migration 命令，也不拒絕。** **否決「寫 migration」**——四份成本（寫、測、出、記錄）換一次性問題不划算；**否決「拒絕舊 task」**——會讓使用者卡在半途，且違反本框架「不覆寫、刪除或重設使用者未要求處理的資料」的硬護欄精神。
- **安裝流程的刪除邏輯只刪「hash 與上一版記錄相符」的檔案。** 沿用 `Uninstall` 已在用的同一條安全規則；使用者手改過的受管檔案不會被覆寫或刪除。`state/knowledge/`、`state/projects/`、task 目錄、`imports/`、`activation.json` 永遠不進 stale 計算。
- **拆檔（逐步揭露）的反向約束：只在「內容明顯大於 pointer 且確實只有部分分支會讀」時才拆。** 拆檔本身有一次額外讀取成本；為了拆而拆會讓常見路徑多付一次 I/O。因此 Elevated 專屬規則、Reviewer 條件式面向／smell 定義、debug 的 feedback-loop 手段清單才拆出去；`codebase-design` 因為內容全部無條件適用，維持單檔不拆。
- **從 mattpocock/skills 只導入 3 個 on-demand skill：`writing-for-agents`、`diagnosing-bugs`、`codebase-design`。** 三者常駐成本只有各自 `description` 一行。**被否決的項目**：
  - `triage` / `to-spec` / `to-tickets` / `wayfinder` / `wizard` — issue tracker 導向，本框架從「task context 已知」起步，且 `unclear_requirements` → `planning` + `grill-me` 已覆蓋
  - `handoff` — 本框架的 `paused` + `stop_reason:` + task.md 唯一狀態源已做得更完整
  - `git-guardrails` — 本框架的 `git_guard.py` + `execpolicy.rules` 已更完整
  - `prototype` — 與本框架的實作／驗證流程重疊，無額外槓桿
  - 每個 skill 一份 `agents/openai.yaml` 的做法 — 本框架的 `adapters/` + `installer.py` 是更集中的跨平台顯示方案
  - **`tdd` 與 `code-review` 的 smell baseline 已在更早之前導入並中文化擴充，比上游版本更完整（含與 workflow／Reviewer／Verifier 的分工），不要重複導入。**
  - **ADR / CONTEXT.md** — 見上一條決策，改用 project-docs 承接而非新增檔案格式

## Open items（刻意不做，附觸發條件）

- **ADR / CONTEXT.md 兩套獨立檔案格式**：不做。若日後 project-docs 的 `decision`／`glossary` doc_type 在實際使用中證明不夠（例如需要跨 repo 共享決策、或需要獨立於 `covers` 機制之外的生命週期），才重新評估。
- **完整重寫 `workflow-policy.json` 的 `scope_rank`／`effect_rank` 語意**：這次只刪掉未被評估的 `candidate`／`suppress_when`，保留 rank 機制本身。若未來需要更複雜的多維度 gating，才需要重新設計。
- **`localization-tw` skill 的內部瘦身**：它是 `.agents/skills/` 最大的單一項目（54%），但屬於 on-demand、常駐成本僅一行 description，且此次分析未深入其內容價值，故不在本次範圍。若之後發現它的觸發率遠低於體積，才需要評估精簡。
- **跨呼叫快取 `resolve_project` 的 git 查詢結果**：Stage 4 把 5 次 git subprocess 合併成 3 次後，`memory-context` 仍有約 150–200ms 花在這些呼叫上。要再壓縮需要在多個共用呼叫者（`git_guard.active_role`、`close_task`、`learn`、`orchestrate`、`memory_context`）之間共享一份短期快取，牽涉 staleness 假設與快取失效時機，風險與範圍超出本次「檔案掃描與注入量」的既定目標。若未來延遲仍是問題，才需要專門評估。
- ~~文件裡 `-Action`／`-Query` 等 PowerShell 風格旗標與實際 argparse 雙連字號小寫不符~~ ——已在「後續補做」一節修正並補上回歸測試，不再是 open item。
- ~~Stage 7 剩餘的可反轉禁止句巡查~~ ——已在「後續補做」一節完成 `planning.md`／`grill-me.md`／`orchestration.md`／`risk-flags.md` 四檔，不再是 open item。
- **`reviewer.md` 面向 3／4／6 是否拆成 `reviewer-conditional-dimensions.md`**：這次重新評估後判斷內容太短（各 1 行）、已有條件句框住，不符合拆檔門檻而沒有做。若未來這三個面向的說明變長（例如補充更多判斷情境），才重新評估是否該拆。

### 後續補做：flag 大小寫 bug 修正 + 剩餘的可反轉禁止句巡查

**修掉一個橫跨文件與程式碼的真 bug**：Stage 5 只改了指令路徑（`scripts/xxx.py` → `agent_workflow.cmd xxx`），沒有核對每個旗標名稱。逐一比對各模組的 `argparse.add_argument` 定義後發現，文件裡大量沿用 PowerShell 風格的 `-Action`／`-Query`／`-Limit`／`-Paths`／`-Doc`／`-RepoRoot`／`-Profile`／`-ApprovedByUser`／`-ConfirmedByUser`／`-Reason`／`-Scope`／`-ProposedChange`，但實際 CLI 是 argparse 雙連字號小寫（`--action`／`--query`…）——單連字號寫法會被 argparse 當成短選項字母串直接報錯，這些指令若真的照文件字面執行全部會失敗。
